## 0. Scope & dependencies

These two stories are authored as **one list** because 06 is a gate-coupled in-band consumer of 05, not a downstream job: 06's two durable writes (`PAYER_SPINE_EXT.first_purchase_day` write-once + `lifetime_spend_normalized` increment; `PAYER_PERIOD_SPEND` increment) execute **inside the same worker step-7 atomic unit as 05's step-6b `PURCHASE_IDEMPOTENCY` gate insert** (bridge [05.5](../001-analytics-platform/bridges/05.5-purchase-accept-contract.md) §1). Story 05 ([006-monetization](./spec.md)) builds the money seam: strict `purchase` validation, the durable `transaction_id` dedup spine, the `MONETIZATION_CELL` (product × dim-combo × day) rollup and `PAYER_DAY` projection, the client-companion `purchase_attempt_id` join with FX as-of normalization and park-unconverted handling, forward-only dimension config with a per-dimension observed-value cap, and the seal-gating reconciliation job. Story 06 ([007-derived-kpis](../007-derived-kpis/spec.md)) is a **pure consumer** that adds only the two payer-bounded structures above and computes every KPI (DAU/WAU/MAU, stickiness, ARPU/ARPPU/ARPDAU, conversion, whale concentration, new/returning) at read time over 02/04/05 results.

**Must exist before start** (umbrella dep table: 05 depends on 01; 06 depends on 02, 05):
- [002-foundation-ingest](../002-foundation-ingest/spec.md) — front-door ingest (canonical envelope, 9-step op-order steps 1–6, catalog/day counts, `EXCEPTION_TALLY` writer, `GAME.config`, `dedup` markers). 05's step-3/6/7/8 are *additions* to this backbone.
- [003-sessions](../003-sessions/spec.md) — `ACTIVE_USER_DAY` + `act` set (all 06 active denominators); the activeness anchor.
- [005-retention](../005-retention/spec.md) — `USER_SPINE.first_seen` (05 server-derivable `days_since_install`/`install_cohort`; 06 new-vs-returning), `COHORT`.
- [009-client-sdk](../009-client-sdk/spec.md) / [010-server-sdk](../010-server-sdk/spec.md) — the SDK contract that mints `purchase_attempt_id` (client companion) and relays it onto the server revenue row, plus the server credential (Foundation §4.5) 05's gate 6a trusts. 05's join and eligibility depend on these being emitted correctly, though 05 can be built and tested against the contract shapes before the SDKs ship.

**Accountable for:** FR-018 (record purchases w/ product, category, normalized price, context dims), FR-019 (rollup by product × dim-combo → top-package-by-D), FR-020 (dims per-game, forward-only on change), FR-021 (server-truth revenue, zero-money client companion joined by key, stands-alone reduced dims), FR-027 (dimension/FX/level-bucket knobs configurable), SC-006 (top-package matches hand-computed rollups), SC-007 (no raw logs; spine stays minimal — 06's two payer-bounded structures are the reconciled draws). 06's KPIs are dashboard-surfaced under FR-025 but define no new FR.

### 1G. Worker pipeline — Step 8 (the join + rollup, one atomic Redis block per event)

- [ ] **T-05.25** **Server-row dimension resolution:** per active dimension resolve — client-only dims (`level_bucket`, `region`, `in_game_state`, `sessions_before_purchase`) from staged `cmp:*` if present else `unknown`; server dims (`payer_tier`, `install_cohort`) from spine/06 state, never client-supplied; **`days_since_install` server-wins** from `first_seen` when a spine row exists, else `unknown` (Q1 never-sessioned). Bucket raw `player_level` against `level_bucket_boundaries` (server-side config) at join time. — *cite:* [design.md](./design.md) Step 8 (server row), spec §2 (dimension resolution), [spec.md](./spec.md) §2.
- [ ] **T-05.26** **FX as-of lookup (Q8):** `rate = fx_rate(currency, purchase_day)` = the most recent `FX_RATE` row with `rate_date ≤ purchase_day`, valid iff `purchase_day − rate_date ≤ fx_staleness_max_days`. — *cite:* [design.md](./design.md) Step 8 (as-of lookup), spec §6 (`fx_table`), bridge [05.5](../001-analytics-platform/bridges/05.5-purchase-accept-contract.md) §2.
- [ ] **T-05.27** **Three-way normalization:** (a) fresh/valid rate → `normalized = price_local × rate`; (b) within-cap stale rate → normalize + tally `fx_stale_rate_used`; (c) missing/over-cap → **park unconverted**: contribute 0 to `rev`, tally `fx_unconverted`; the amount still increments `cnt`, `loc`, the `payer` set, and day `loc:*` totals. Count-vs-normalization degrade independently; money never blocked. — *cite:* [design.md](./design.md) Step 8 (three-way), Foundation §1.2 `EXCEPTION_TALLY` reasons (`fx_stale_rate_used`, `fx_unconverted`).
- [ ] **T-05.28** **Atomic rollup block (server row):** increment cell `cnt`/`rev`/`loc`, add payer to `payer` set, add to `rev` day totals, write `srv:*` staging, clear consumed `cmp:*` — one atomic Redis block. `payer_attempt_id`-keyed staging holds `srv:*` so a later companion can enrich. — *cite:* [design.md](./design.md) Step 8 (atomic block).
- [ ] **T-05.29** **Companion — enrichment MOVE** (`srv:*` staged AND purchase day unsealed): recompute `dim_combo` replacing only client-sourced components (server-derived frozen at count time); if changed, atomically decrement old cell `cnt`/`rev`/`loc` and increment new cell, update `srv:dim_combo`, `INCR` `gen`. A move **conserves count and revenue** — enrichment never changes money. This is why `mon`/`rev`/`loc` are class-N (mutable-down) and `GREATEST` is forbidden. — *cite:* [design.md](./design.md) Step 8 (enrichment move), Foundation §3.2.1 class N.
