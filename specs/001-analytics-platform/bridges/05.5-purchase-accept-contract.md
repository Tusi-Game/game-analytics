# Bridge 05.5 — Purchase-Accept Contract (05 ↔ 06)

**Feature**: 001-analytics-platform · **Layer**: design bridge (cross-story contract) · **Status**: Design-complete (2026-07-17)
**Parties**: Phase 05 — **owns** the durable `transaction_id` gate (`PURCHASE_IDEMPOTENCY`, step 6b) and emits the purchase-accept signal · Phase 06 — **owns** `PAYER_SPINE_EXT` + `PAYER_PERIOD_SPEND`, written in-band on that signal.
**Grounding**: Foundation §3.1 steps 6–7, §4.1, §4.5, §5 (durable-immediate both, gate-coupled); [006 monetization design](../../006-monetization/design.md) steps 6–7; [007 derived-kpis design](../../007-derived-kpis/design.md) coupling point.
**Why a bridge**: the money seam — one gate outcome triggers durable writes for two stories inside one worker step, plus a read-before-write ordering (`payer_tier`). Both sides flagged it; this file is normative for both.

---

## 1. The seam, in one normative statement

> "Purchase accept" = 05's durable `PURCHASE_IDEMPOTENCY` insert-if-absent **succeeding** (step 6b, after the 6a eligibility filter: `verified=true` ∧ `environment=prod` ∧ server-credential provenance, Foundation §4.5). The accept **signal** is emitted after the durable insert and is **at-least-once** (crash-resume may re-emit). 06 consumes it **in-band, in the same worker step 7** — never via a fan-out consumer — and its two durable writes are **bound into the same atomic unit as the gate insert**: gate row + `first_purchase_day` write-once + `PAYER_PERIOD_SPEND` increment commit together or not at all. **Net effect: exactly-once application** — a duplicate dies at the gate (insert conflicts ⇒ the unit no-ops wholesale, so the increment never re-applies), and a crashed unit either fully re-runs (nothing committed) or fully no-ops (everything committed).

This supersedes the two stories' separate phrasings — 05's "at-least-once signal, consumers idempotent per `transaction_id`" and 06's "atomic unit" — which describe the same behavior; the atomic unit is **how** the per-txn idempotency is achieved for a cumulative (non-idempotent) increment. Deliberately stronger than step 7's "idempotent absolute" letter, as a cumulative money distribution requires.

## 2. Signal payload (normative)

| Field | Source | Consumed by 06 for |
|---|---|---|
| `game_id`, `user_id` | gate row | keys of both writes (**spine-independent** — the payer row may exist with no `USER_SPINE` row; Q1 consequence, §3) |
| `transaction_id` | gate row | the idempotency scope of the whole unit |
| `purchase_day` | corrected UTC day (Foundation §4.2) | `first_purchase_day` value; `period = month(purchase_day)` |
| `price_local`, `currency` | gate row | audit / re-derivation consistency |
| `normalized_amount` | `price_local × fx_rate(currency, purchase_day)` under **as-of FX lookup** (Q8, §6b), stamped by 05; **may be 0** when no in-cap rate exists (amount parked unconverted) | the `PAYER_PERIOD_SPEND` **and** `PAYER_SPINE_EXT.lifetime_spend_normalized` increments — consumers MUST tolerate a 0/parked value (adds nothing to cumulative spend until a rate lands pre-seal, §6b) |
| `product_id` | gate row (05 story-added attribute) | none in v1 — carried for signal completeness / future per-product payer cuts |

**Deliberately NOT in the payload**: `original_transaction_id` (rides the idempotency row; consumers needing it read the row), `is_first_purchase` (**derived by 06's own insert-if-absent**, never trusted from a signal — the write-once outcome is the truth), `payer_tier` (05-internal display dimension, §3), `purchase_attempt_id` (the **context-join** key, 08 §3.2 / 09 — used by 05's step-8 companion join, not by 06's spend writes; it rides the server revenue row, not this signal).

**FX-parked spend interaction (2026-07-17):** when `normalized_amount` is 0/parked (missing FX rate), 06's `lifetime_spend_normalized` increment adds nothing **and 06 sets `PAYER_SPINE_EXT.has_unconverted_spend = true`** — so the payer's `payer_tier` reads `indeterminate` (never a deflated `minnow`) until the parked amount converts pre-seal and the flag clears (the whale-mis-tier fix; 05 step 7, 06 step 7). Both spend increments already tolerate a 0 value (§2, §8 checklist).

## 3. Ordering (normative)

Within one accepted purchase's processing:

```
6a eligibility → 6b gate insert (unit opens) → payer_tier READ (pre-purchase state)
   → 06 writes: first_purchase_day write-once; lifetime_spend_normalized += normalized_amount;
                PAYER_PERIOD_SPEND += normalized_amount
   → unit COMMITS → 05 step-8 hot writes (mon/payer/rev cells, stage marker)
```

- **05 reads `payer_tier` from PRE-purchase state** — `PAYER_SPINE_EXT` existence + **`lifetime_spend_normalized`** (Q3, §6) vs `payer_tier_rule` thresholds — strictly **before** 06's writes mutate payer state. Inverting this misclassifies every first purchase as `repeat`. Tiering is count-time only, never retro-applied.
- **Spine-independent (Q1, 2026-07-17):** `first_seen` is seeded only by 02's first-session path (bridge 02.5 §6), so a purchase-before-first-session (or a never-sessioned payer) opens this unit with **no `USER_SPINE` row**. The payer family keys on `(game_id, user_id)` as a logical association, not an enforced spine-parent FK; `first_purchase_day` may precede (or exist without) `first_seen`. Money is never blocked on engagement state. `PAYER_SPINE_EXT → PAYER_PERIOD_SPEND` existence order still holds within this unit.
- **Crash-resume interaction** (05's 6b rule): on gate conflict with the `stage:{transaction_id}` `srv:*` marker absent on an unsealed day, the retry **resumes at step 8 only** — the durable unit no-ops (already committed). Residual: the resume re-reads payer state *post*-mutation, so the display cell's `payer_tier` dimension can tier one crash-window purchase as `repeat` instead of `first` — display-only drift, same class as 05's residual-drift open question; the durable structures are unaffected.

## 4. Failure ledger

| Interleaving | Gate row | 06 writes | Outcome |
|---|---|---|---|
| duplicate `transaction_id` (any lateness) | conflict | not run | stop — exactly-once preserved, no signal re-fired downstream effects |
| crash before unit commit | absent | absent | retry re-runs the whole unit — nothing was durable |
| crash after commit, before step 8 | present | present | retry resumes display writes only (marker-absent rule); money exact, display heals |
| Redis total loss | present | present | untouched — nothing of this contract lives in Redis (06 owns no keys; 05's stage is enrichment-only) |

## 5. Provenance precondition

The signal exists **only** for rows accepted under the **server-scope credential** (`GAME_SERVER_CREDENTIAL`, Foundation §4.5 — credential-class-derived, never body-trusted; **F-3 resolved 2026-07-17**, Q2). Server credentials are always distinguishable (secret, prefix-typed, 1..N per game — phase 10), so the earlier "idle if indistinguishable" failure mode no longer applies; the fallback-`client` rule survives only for a valid-but-unclassifiable legacy edge, which never passes 6a.

## 6. DECISION RECORD — payer-tier cumulative spend = LIFETIME (RATIFIED 2026-07-17, research-locked)

**The gap (now closed)**: 05's `payer_tier_rule` tiers a purchase by **cumulative spend at count-time** (first / repeat / whale), but the only durable cumulative structure was 06's `PAYER_PERIOD_SPEND` — period-scoped (calendar month), which resets every month-boundary; summing all periods at count-time is an unbounded-window hot-path read.

**Decision.** Add a **lifetime cumulative-spend field on `PAYER_SPINE_EXT`** — `lifetime_spend_normalized` (monotonic non-decreasing; incremented by `normalized_amount` inside this contract's atomic unit, alongside `first_purchase_day` and the `PAYER_PERIOD_SPEND` increment). Tiers derive from this number at read time against operator-configured **fixed dollar thresholds** in `payer_tier_rule` (store the spend, **never** the tier label). Windowed/monthly cuts remain fully available as derived reads over the already-budgeted `PAYER_PERIOD_SPEND` — no new state for them.

**Why lifetime, not windowed.** The industry's canonical tier definitions are lifetime: deltaDNA's standard whale = ">$100 **lifetime** spend"; devtodev and GameAnalytics segment by *total* spend (fixed thresholds or percentile cuts of cumulative spend); RevenueCat's customer value = cumulative realized LTV. Whale status accretes — deltaDNA found 54 % of whales never made a single >$50 transaction — so a windowed tier structurally misses steady accumulators. "Payer vs non-payer" is itself lifetime-anchored (payer-ness never resets), so tiers within it resetting monthly is incoherent. Demotion ("a lapsed whale") is handled by layering **recency** (RFM) over the sticky lifetime tier — derivable from `PAYER_PERIOD_SPEND` (zero recent periods) with zero extra state. Percentile tiering is rejected for the spine (unstable for one self-hosted game with few payers, nondeterministic at count-time, retroactive by construction); percentile *views* (whale concentration, top-k) stay available downstream.

**Fixed-threshold posture (default, all `payer_tier_rule`-overridable):** non-payer = no `PAYER_SPINE_EXT` row; minnow = lifetime < $10; dolphin = $10–$99.99; whale = ≥ $100 (the deltaDNA anchor). Threshold edits re-tier all *future* reads immediately at zero migration cost (the spine stores spend, not tier); count-time tier stamps on already-written display cells remain forward-only (§3, never retro-applied).

**Ledger amendment (landed):** one new payer-bounded line in [`../spine-budget-ledger.md`](../spine-budget-ledger.md) — "lifetime cumulative normalized spend, keyed per payer, 1 small numeric, payers ≪ users". Row-existence remains the payer/non-payer boundary; non-payers cost zero. Rebuildable from `PURCHASE_IDEMPOTENCY` + dated FX like its siblings (§8). Both rejected options — tier-by-current-period (whale resets monthly) and 05-keeps-its-own-tier-state (cross-ownership drift) — stay rejected.

*Sources: deltaDNA/PocketGamer.biz (whale = >$100 lifetime; 54 % never >$50/txn) · devtodev "4 Methods of Paying Audience Segmentation" (total-payments tiers) · GameAnalytics "How to find the whales" (percentile cuts of total spend) · Game Developer "spending patterns of whales" (cumulative accretion) · RevenueCat realized-LTV docs (cumulative value + RFM recency layering).*

## 7. Worked example (user `u9`, month 2026-07, whale threshold $100 cumulative)

| Event | Gate (6b) | Tier read (pre-purchase) | Atomic unit commits | Post-state |
|---|---|---|---|---|
| T1 $4.99, u9's first ever | insert OK | no `PAYER_SPINE_EXT` row → **`first`** | gate row + `first_purchase_day = purchase_day` + `lifetime_spend 0 → 4.99` + period spend `0 → 4.99` | payer exists, lifetime 4.99 |
| T2 $9.99, same day | insert OK | row exists, **lifetime** 4.99 < 100 → **`repeat`** | gate row + first-purchase **no-op** (write-once) + `lifetime 4.99 → 14.98` + period `4.99 → 14.98` | lifetime 14.98 |
| T2 retried by SDK (3 days later) | **conflict**, `srv:*` marker present | — | **nothing** — true duplicate, stop | unchanged — exactly-once held |
| T3 $0.99, crash after commit, before step 8 | retry: conflict, marker **absent**, day unsealed | *(resume re-read sees post-state — §3 residual)* | already committed; resume runs step 8 only | money exact; display cell heals |

The tier read consults `PAYER_SPINE_EXT.lifetime_spend_normalized` (§6 ratified) — the whale threshold ($100) is evaluated against lifetime, so a steady spender crosses it across months without the tier ever resetting.

## 8. Conformance checklist (what a reviewer verifies in 05 / 06)

- [ ] 6a eligibility (verified ∧ prod ∧ server-credential provenance) runs strictly before 6b — ineligible rows never consume a `transaction_id` slot.
- [ ] The `payer_tier` read precedes 06's mutations in every path, including resume (residual documented, §3).
- [ ] 06's two writes appear nowhere outside the gate-coupled atomic unit; no fan-out consumer exists.
- [ ] Signal payload matches §2 exactly; nothing consumes `is_first_purchase` from a signal.
- [ ] Duplicate `transaction_id` produces zero durable effect in either story, at any lateness.
- [ ] `PAYER_PERIOD_SPEND` and `PAYER_SPINE_EXT` (incl. `lifetime_spend_normalized`) re-derive from `PURCHASE_IDEMPOTENCY` + dated FX (rebuild lever intact).
- [ ] `payer_tier` read consults `lifetime_spend_normalized` against `payer_tier_rule` fixed thresholds — never the period row, never a stored tier label.
- [ ] The payer family keys `(game_id, user_id)` with no enforced `USER_SPINE` parent — a never-sessioned payer commits the unit normally; a 0/parked `normalized_amount` (missing FX rate) adds nothing to cumulative spend and is tolerated by both spend increments.
