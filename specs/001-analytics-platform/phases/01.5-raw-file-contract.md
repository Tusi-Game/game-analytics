# Bridge 01.5 — Raw Day-File Contract (01 ↔ 07)

**Feature**: 001-analytics-platform · **Layer**: design bridge (cross-story contract) · **Status**: Design-complete (2026-07-17)
**Parties**: Phase 01 — **executes** the write-ahead append (Foundation §3.1 step 4, in every ingest worker) · Phase 07 — **owns** file semantics + the disk → S3 → delete lifecycle.
**Grounding**: Foundation §3.1 step 4, §4.3–4.4, §6; [01 Design](01-ingest-raw-events.md) worker step 4; [07 Design](07-cold-storage.md) ER lifecycle + flows (a)/(b); §E / SC-008 / SC-010 / US5.
**Why a bridge**: both sides flagged it — silent drift between the append 01 executes and the semantics 07 owns breaks SC-008 without any single-story test tripping. Everything below is **normative for both stories**; their Designs cite it, never re-derive it.

---

## 1. Ownership split

| Concern | Owner | Executor |
|---|---|---|
| Append ordering (write-ahead ≺ any counter/spine/Redis write), per-event append position, quarantine-vs-drop verdict | 01 (front-door) | 01 workers |
| File semantics: routing, open/seal states, marker vocabulary, fsync grain, codec, superset guarantee definition | 07 | 01 workers (append) |
| Lifecycle: seal → upload → verify → bookkeeping → local delete; ops read-model | 07 | nightly job |

**No 07 writer exists on the hot path** — every record reaches the file through 01's single step-4 append; 07 never touches an open file.

## 2. Routing (normative)

- **Per game × corrected UTC day, among OPEN files only.** An event's file is chosen by its skew-corrected day (Foundation §4.2). Under the §G 48 h grace this means **≤ 3 open files per game** (today + 2 grace days), mirroring Foundation §2.3's ≤ 3 open buckets.
- **Sealed-late events quarantine-append to the CURRENT processing-day's open file** — the marker records the offending corrected day (§3). **No append ever targets a sealed file.** This is 07's Design decision, made normative here: once day D seals, D's file is immutable and upload-eligible, so the 01 → 07 handoff needs **no lock, no handshake, no re-open** — 01 only ever writes files 07 never reads, and 07 only ever ships files 01 never writes.
- **A day with zero events (or cold storage off) never instantiates a file**; nothing compensates later (forward-only).

## 3. Record classes + quarantine-marker vocabulary (normative)

| Class | Content | In file? | Tally |
|---|---|---|---|
| **Body** | full canonical envelope, verbatim (Foundation §1.1) — every event that will be counted, **including duplicates** (§5) | yes | — |
| **Quarantine** | full envelope + **marker**: `reason ∈ {quarantined_typed, sealed_late}` + the event's corrected UTC day | yes (same file, marker-tagged) | `EXCEPTION_TALLY`, same reason |
| **Drop** | unparseable / nameless / cap-exceeded — events that could never count (Foundation §4.4) | **never** | `nameless` / `unparseable` / `capexceeded` |

- The marker vocabulary **equals the `EXCEPTION_TALLY` reason names** — one vocabulary across file and tally, no mapping table. The quarantine "tail" is **logical, not physical**: the region selected by marker within the one day file; byte layout is format-phase territory.
- Marker append happens at the same write-ahead position, **before** the corresponding tally increment.

## 4. Append mechanics (normative)

| Rule | Contract |
|---|---|
| Ordering | fsync'd append **before any counter, spine, money, or Redis write for the same batch** (§E; Foundation §3.1 step 4). Counter-first is a bug. |
| Fsync grain | per-event append, **one fsync per dequeued batch**. The superset guarantee holds at batch grain: an event is counted only after its batch's bytes are durable; a crash between fsync and count loses counts, never log entries — the safe direction (SC-008). A **single dedicated append-writer per open file** serializes appends (one file, one writer — avoids interleaved/torn gzip members from concurrent workers) and **coalesces multiple workers' appends into one fsync (group commit)**, so a hot single game does not collapse worker concurrency to one; workers hand buffers to the writer. |
| Compression + framing | gzip append (`raw_file_compression`); a file keeps the codec it was **opened** with — codec changes are forward-only, next day's file. **Each batch append is a self-contained, length-prefixed gzip member** (framed record stream), so a crash mid-append leaves a *detectable* truncated trailing member that rebuild tooling **skips with a loud warning**, never silently drops. Rebuild tooling MUST be **multi-member-safe** (iterate every concatenated member; some decoders silently discard members after the first — forbidden) and **fail loud** on a bad tail. |
| Seal-time integrity | at seal, before a file is marked upload-eligible, the nightly/seal path **verifies the file decodes end-to-end** (every member) and records the result in `integrity_ref` — a decode-check, not just a checksum. A file that fails end-to-end decode is flagged for operator attention, not shipped as a valid rebuild floor. |
| Rotation | a file opens at the first append for its day and closes at that day's seal (§6). No intra-day rotation. |

## 5. Duplicates and the rebuild floor

**Duplicates DO appear in the raw file** — the append (step 4) precedes the dedup gates (step 6) by design. A manual rebuild therefore **re-dedups**: by `event_id` (windowed semantics) for non-money, by `transaction_id` (durable semantics) for purchases. The file is a superset, not a deduplicated log; rebuild tooling must never sum it blindly.

### 5.1 Manual rebuild procedure (normative outline — the recovery floor made concrete, 2026-07-17)

SC-008, Foundation §6, and the Q7 erasure design all name the manual raw-file rebuild as the recovery floor, but v1 ships **no automated replay**. This subsection makes the *procedure* concrete (the tool build is deferred, but the steps are specified so "disposable but recoverable" is real, not aspirational). To rebuild a day `D`'s aggregates from its raw file(s):

1. **Decode safely** — iterate every gzip member (multi-member-safe, §4); a truncated trailing member is skipped with a warning, never silently dropped.
2. **Per-record wire dispatch** — read the stamped wire `v` on each record (Foundation §1.1) and normalize through the version's reader (additive-only, so v1 is stable).
3. **Re-dedup** — by `event_id` (drop repeats) for non-money; by `transaction_id` for purchases (money never double-counts).
4. **Re-apply the erasure filter** — for each record, compute the per-game keyed hash of its `user_id` and **skip on a match with an `executed` `ERASURE_LEDGER` row** (00.5 §7.3 — "put beyond use" on rebuild). This step is mandatory; a rebuild that skips it re-materializes erased data.
5. **Skip quarantine-marked records** for aggregate rebuild (they were excluded from the sealed cells by design); they remain available for a separate inspection pass.
6. **Re-derive with logical-day flooring** — bucket each record by `logical_day(corrected)` (Foundation §4.7) exactly as the live pipeline did, so a rebuilt cell matches the sealed cell.
7. **Reconcile-forward only** — a rebuilt cell may read *below* a sealed cell after erasure (correct — post-erasure spine is the truth); a rebuild never rewrites a sealed cell downward to match (00.5 §7.6). Dimension-resolved monetization cells cannot be exactly rebuilt from raw alone where companion joins were involved — the documented limitation (05).

The tool itself is deferred to a later phase; this outline is its normative contract, referenced by SC-008, Foundation §6, 00.5 §7.3, and §11 below.

## 6. File lifecycle × seal (normative)

```
OPEN      first append for day D → body + quarantine appends during D and its 48 h grace
COMPLETE  at seal(D) = D_end + 48 h — file immutable; upload-eligible from this moment
UPLOADED  nightly job: upload → verify (integrity_ref) → UPLOAD_BOOKKEEPING row (verify-then-record)
DELETED   after uploaded_at + cold_storage_local_retention_days; never without a verified row
```

- **Upload-eligibility = SEALED file.** The nightly job ships every **newly-sealed** day — under the default 48 h grace that is day `run_day − 3` (plus any catch-up backlog; eligibility is state-derived, so missed runs self-heal). Shipping earlier would ship an incomplete file: grace arrivals for D would be counted-but-unshipped, breaking the SC-008 superset *in the object*, or force object rewrites.
- **RESOLVED (2026-07-17, research-ratified — Q4): upload-eligibility = sealed file.** US5/SC-010's "**yesterday's** file" is read as "the most recent **completed (= sealed)** file" — nightly cadence honored, eligibility clock aligned to the seal (`run_day − 3` under the default 48 h grace). Ratified against industry practice: shipped objects are final everywhere — Kafka Connect's S3 sink uploads only rotated/closed files (commit-after-upload, deterministic keys, retry = idempotent overwrite); GA4's BigQuery daily export lands well after midnight and keeps absorbing late events for ~72 h (*longer* than our 48 h seal) — it can patch post-delivery only because BigQuery is a mutable warehouse, and covers freshness with a separate intraday table (our Redis open-day buckets are exactly that analog); systems that ship immediately (Firehose, Snowplow lake loaders) buy it by partitioning on *arrival* time, not event time. Event-time-keyed objects ship at watermark/seal — the standard branch. S3-compatible objects are immutable (PUT = full replace; append exists only in S3 Express One Zone directory buckets, irrelevant for MinIO-class targets), so shipping early would mean whole-day object rewrites on every grace arrival, or a silently broken SC-008 superset *in the object*. SC-010's behavioral test passes under this reading; an operator insisting on literal yesterday must set grace = 0 — a spec change, not a design change. *Sources: Confluent S3 Sink Connector docs (rotation / commit-after-upload); Google Analytics Help — [GA4] BigQuery Export (daily/intraday table timing); AWS S3 docs (object immutability, append constraints); Snowplow docs (lake-loader load-time partitioning; late-arriving data); AWS Firehose buffering FAQs.*
- Local disk consequence: ~3 open files + the retention-window sealed files per game.

## 7. Cold-storage-off behavior (normative)

`cold_storage_enabled = off` ⇒ step 4 is a **no-op**: no file, no fsync, no lifecycle, no bookkeeping. Counters, spine, money, and tallies proceed unchanged; quarantine-destined events become **tally-only**. The SC-008 superset guarantee is **waived — operator-accepted** (US5 scenario 3). Toggle is forward-only: on-mid-day starts a partial file (ships normally, labeled by its lifecycle alone); off-mid-day stops appends but an already-open file completes its normal lifecycle.

## 8. SC-008 statement (the invariant this contract exists to protect)

> The raw day file is a **complete superset of everything counted** for its day: `file = body (everything counted, duplicates included) ∪ quarantine (recoverable-but-excluded)`. Drop-and-tally events are deliberately outside it — they could never count. No event is ever counted-but-unlogged; the file is a valid manual rebuild floor for its day, and only for its day.

## 10. Failure interleavings (both stories test against these)

| Failure | Outcome | Why safe |
|---|---|---|
| crash between fsync and count | logged-but-uncounted (≤ 1 batch) | undercount direction; raw floor intact |
| crash mid-upload / mid-verify | no bookkeeping row → next run re-uploads to the **same** `object_ref` | overwrite-idempotent; no partial state recorded |
| Redis loss | file unaffected (disk, written ahead) | write-ahead ordering |
| local file lost pre-upload | that day's rebuild floor gone, results intact | accepted loss (US5; Foundation §6) |
| sealed-late arrival | quarantine-append to current open file, marker carries corrected day | sealed objects never mutate (§2) |

## 11. Conformance checklist (what a reviewer verifies in 01 / 07)

- [ ] 01's step 4 routes by corrected day among open files only; sealed-day verdicts append to the current open file with a `sealed_late` marker.
- [ ] No code path opens, appends to, or rewrites a COMPLETE/UPLOADED file.
- [ ] Fsync precedes every counter/spine/Redis write for the same batch; one fsync per dequeued batch.
- [ ] Marker reasons are exactly the `EXCEPTION_TALLY` names; drop-class events never reach the file.
- [ ] 07's job selects sealed ∧ unbookkept days (state-derived, catch-up safe); verify-then-record; delete only after a verified row + retention.
- [ ] Cold-off ⇒ step 4 no-op everywhere — no half-written lifecycle states.
- [ ] Each batch append is a length-prefixed self-contained gzip member; rebuild tooling is multi-member-safe and fails loud on a truncated tail (§4).
- [ ] Seal-time end-to-end decode verification runs before a file is upload-eligible; `integrity_ref` records it (§4).
- [ ] A single dedicated append-writer per open file serializes appends and group-commits fsyncs (§4).
- [ ] The §5.1 rebuild procedure re-dedups AND re-applies the `ERASURE_LEDGER` filter AND floors by logical day; reconcile-forward-only holds.
