## 1. Purpose

The story designs (01–07) fixed *what* is computed and *where* state lives; none of them said **how much**, **what happens when a store is full or down**, or **what the platform does when a data subject demands erasure**. This spec pins those three things:

1. A **defensible scale envelope** (§2) and the **Redis memory budget** derived from it (§3) — the numbers Foundation §2.3's "≤ 3 open buckets", §3.2's `noeviction` posture, and §F's dedup sizing were implicitly assuming.
2. The **failure posture** (§4–§5): queue-depth bounds, what the fast-ack door does when Redis is full or Postgres is down, and a new per-game rate-limit knob so one tenant cannot flood the shared budget.
3. The **normative GDPR/CCPA erasure design** (§7) — the home of the Q7 ruling referenced by Foundation §9.6 and research §7.

Everything here is a **baseline, not a guarantee**: the envelope states the load v1 is engineered for and the trigger points (§6) at which the named scale levers flip. Exceeding the envelope is a capacity decision, not a correctness failure — the invariants (write-ahead raw, durable-immediate money, absolute flush) hold at any scale; only headroom shrinks.

## 2. Target scale envelope

Assumptions are explicit and deliberately indie-shaped (the platform's stated audience — solo/small operators on a modest VPS):

| Assumption | Value | Basis |
|---|---|---|
| Registered games | 25 (≈ 20 meaningfully active) | multi-tenant, one operator |
| DAU per active game | median ~2,500; single-game design ceiling 20,000 | indie scale |
| Platform DAU (Σ over games) | **~50,000** | 20 × 2,500 |
| Events per DAU per day | **150** (≈ 4 sessions + generic gameplay events) | mid-range of the 100–500 industry norm |
| Batch size (SDK default) | ~25 events/batch | 08/09 SDK batching |
| Daily payer conversion | ~2 % of DAU | conservative indie |
| Distinct currencies | ≤ ~10 virtual first-class per game (03's cap + `other`); ≤ ~30 ISO local currencies platform-wide | §2.3 observed-value cap |

**Derived load (shown):**

```
expected events/day  = 50,000 DAU × 150 ev/u/d           = 7.5 M events/day
budget line          = 10 M events/day                    (the research §F anchor; ×1.33 headroom,
                                                           and §F's dedup sizing carries over unscaled)
mean rate  @ budget  = 10,000,000 / 86,400 s             ≈ 116 events/s
peak factor          = ×5                                 (evening peak + offline-batch lumpiness)
design peak          ≈ 580 → round to 600 events/s        ≈ 24 batch-POSTs/s at 25 ev/batch
purchases/day        = 2 % × 50,000                       = 1,000/day  ≈ 1 per 86 s mean, ~10/min peak
```

Every budget below is computed at the **10 M events/day budget line**, not the 7.5 M expectation. A single NestJS ingest node and a single modest Postgres absorb this trivially; the binding constraint is **Redis memory**, budgeted next.

## 3. Redis memory budget

Redis runs `maxmemory-policy noeviction` + AOF `everysec` (Foundation §3.2 / research §E) — nothing is ever silently evicted, so the budget must be explicit and the door must brake before OOM (§4). Components at the §2 budget line:

| Component | Arithmetic | Budget |
|---|---|---|
| **Dedup markers** (24 h SET-with-TTL, Foundation §2.3) | research §F: **~0.4–0.6 GB/day at 10 M events/day**; steady state ≈ one day's markers | **0.75 GB** (§F's upper figure + margin for long `event_id`s) |
| **Open-day counter buckets** (≤ 3 open days × ~10 domain structures/game — Foundation §2.3's ≤ 3-bucket, ~72 h-TTL rule) | worst-case ~10 k hash fields/game/day (cnt ≤ 500 names, eco ≤ ~800 cells, mon cap-bounded ≤ ~5 000, ret ≤ horizon, exc/sess small) × ~100 B ≈ 1 MB/game/day × 3 days × 20 games = 60 MB | **0.10 GB** |
| **Membership sets** (exact `user_id` sets — `act` + `payer` open days; the structure Foundation §9.2's HLL lever exists for) | Σ DAU × 3 open days × ~100 B/member = 50 k × 3 × 100 B = 15 MB | **0.02 GB** |
| **Companion staging** (48 h TTL, 05) | ≤ 2 days × 1,000 purchases × ~0.5 KB | **< 0.01 GB** |
| **BullMQ steady state + AOF-rewrite buffers + fragmentation** | ~25 % operating overhead | **0.60 GB** |
| **Queue backlog headroom** | remainder | **~2.5 GB** ≈ 250 k batch jobs ≈ **6 M enveloped events** |
| **Instance total** | | **4 GB** (`maxmemory` ≈ 3.8 GB; door watermark at 80 % ≈ 3 GB, §4) |

Readings: steady-state occupancy is **~1 GB** — dedup markers dominate, exactly as §F predicted; counter buckets and membership sets are noise *at this envelope* (they are the levers of §6 precisely because they scale linearly with names×cells and DAU respectively, while dedup scales with raw event volume). The remaining ~2.5 GB is deliberately reserved as **queue backlog** — that headroom is the platform's outage tolerance, quantified in §4.

## 4. Queue-depth bounds and backpressure posture

**Normal operation.** Workers drain at wire speed; BullMQ depth is near zero (600 ev/s design peak is ~24 jobs/s against workers doing cheap per-event work). Depth is a health signal, not a working buffer.

**Backlog bound.** The §3 headroom holds ≈ 6 M events ≈ **~14 h at budget mean / ~3 h at design peak**. Two soft limits trip the door before `noeviction` OOM: **used-memory watermark 80 % of `maxmemory`** and **queue depth ~200 k jobs**, whichever first.

**Redis approaching full → reject at the door, never shed after ack.** Foundation's fast-ack (FR-006, 01: "a queue-acceptance receipt") means the 202 is a promise the batch is *in the queue*. Therefore:
- Past the watermark, the ingest API returns **503 + Retry-After** *before* acking — the SDK already owns offline buffering and backoff (08/09), so a 503'd batch is retained client-side and retried; nothing acked is ever dropped. Fast-ack **degrades to fast-refusal**, never to silent shed.
- The watermark exists because `noeviction` OOM is indiscriminate: at 100 % *all* writes fail — dedup markers, open-day buckets, spine-path staging — corrupting live counting to save a queue. Capping the queue below `maxmemory` keeps the counting path alive while the door sheds load.
- If Redis is fully down: the door cannot enqueue → 503 everything. No data loss (nothing was acked); in-flight loss on a crash stays ≤ 1 s AOF window per Foundation §6.

**Postgres down → a latency event, not a loss event.** The write-ahead ordering (Foundation §3.1 step 4 / bridge 01.5) means the bytes are on disk *before* any durable write is attempted:
- **Durable-immediate writes fail → BullMQ retries the job** with backoff (at-least-once). For **money** this is exactly safe: step 6 *is* the failing Postgres insert, so no dedup marker swallows the retry; the durable gate + write-once/monotonic absolutes make eventual application exactly-once (bridge 05.5). For **non-money**, a job that set its 24 h marker before failing may no-op on retry — a bounded undercount already accepted in 01's idempotency note; the raw file still holds the event.
- **The flush stalls harmlessly**: open-day buckets keep accumulating absolute values; the absolute upsert (Foundation §3.2) catches up idempotently on recovery. Day-seal is gated on a successful final flush, so seals defer rather than finalize short.
- **Bound**: the queue headroom rides ~3–14 h of outage (above); the ~72 h open-bucket TTL bounds how long the hot layer can defer flushing before the manual raw-rebuild floor (Foundation §6, bridge 01.5) becomes the recovery path. Beyond the watermark, the door 503s and events wait client-side.

Cross-check against the Foundation §6 loss ledger: no row changes. Backpressure converts "would-be loss" into SDK-side retention; Postgres outage converts into queue latency; the accepted-loss lines (≤ 1 s AOF, ≤ flush-cadence drift, local-file loss) stay exactly as written.

## 5. Per-game rate limiting — `ingest_events_per_sec_cap` (new knob)

The §4 watermark is a *global* brake: by the time it trips, every tenant is refused. Multi-tenancy needs a *per-tenant* brake that trips first, so one flooding game (a bug spamming events, a hostile client on the public `sdk_key`) consumes its own cap instead of the platform's.

| Property | Value |
|---|---|
| Knob | **`ingest_events_per_sec_cap`** — per-game, in `GAME.config`, **forward-only** (repo convention) |
| Default | **200 events/s sustained** per game ≈ ⅓ of the §2 design peak, ~7× a game's fair share (600/20 = 30 ev/s) — generous for any legitimate tenant, strictly < the platform budget |
| Mechanism | token bucket at the door, counted in **events** (batch size varies; events are the cost driver), refill 200/s, **burst allowance 5,000 events** — absorbs a returning offline client flushing a multi-thousand-event buffer without tripping |
| On breach | whole batch **429 + Retry-After** (admit-or-refuse atomically, never partial); increment a **`rate_limited`** tally — proposed as an `EXCEPTION_TALLY` reason-enum addition (same amendment path `time_fallback` took), arrival-day bucketing per 01's rule |
| Raw file | refused batches are **never raw-appended** — this is flow control, not a verdict; the SDK retains and retries, so nothing countable is lost (SC-008 unaffected) |
| FR-006 | preserved for good tenants — the check is a local O(1) token-bucket read pre-ack, no Postgres touch; a well-behaved game never observes it |

**Why per-game, not global:** the shared structures (queue, dedup marker space, flusher bandwidth) are platform-wide; a global limiter lets the noisiest tenant starve the quiet ones and gives the operator no lever short of key revocation (an emergency action, Foundation §4.5). Per-game caps convert a neighbor-flood into that game's own 429 stream — visible in its own tally — while the §4 watermark remains the last-resort platform brake behind it.

## 6. Scale-lever trigger points

Each lever is already named in the foundation/research; this section pins **when** to flip it, derived from the §3 budget. All levers are forward-only and none ever touches money or retention truth.

| Lever | What flips | Trigger (derived) | Cost of flipping |
|---|---|---|---|
| **HLL for membership / user-counts** (Foundation §2.2 palette, §9.2) | open-day `act`/`payer` exact sets → `PFADD` sketches (~12 KB fixed vs ~100 B/member) | open-day membership > ~5 % of instance: Σ DAU × 3 × 100 B > 200 MB ⇒ **platform DAU ≳ 650 k**, or any single game **DAU ≳ 200 k** | exact same-day distincts become ±~0.8 % estimates; exact window-unions (WAU/MAU set-union in 06) become HLL merges |
| **HLL-drops-sealed-membership** (Foundation §9.2's second half) | sealed `ACTIVE_USER_DAY.members` / `PAYER_DAY.payer_members` stop retaining `user_id`s — counts (or sketches) only | sealed membership growth becomes material in Postgres: DAU × ~25 B × 365 d ⇒ ~0.5 GB/yr at the §2 envelope (fine for years) vs **~9 GB/yr at 1 M DAU** — flip at ≳ 500 k DAU or on privacy-posture preference | historical exact window-unions and membership listings gone; **shrinks the §7 erasure surface** — sealed days then hold no per-user identifier to scrub, and the erasure job's membership pass reduces to open/recent days only |
| **RedisBloom for dedup** (research §F; **never money** — a false positive silently drops a real event; purchases keep the durable gate regardless) | 24 h SET markers → Bloom (~12–24 MB/day, 25–40× smaller) | dedup steady state > ~⅓ of instance: > 1.25 GB ⇒ **≳ 25–30 M events/day** (per §F's 0.4–0.6 GB per 10 M), *and* upsizing the instance is unattractive | ~1-in-10³–10² non-money events falsely deduped (§F-4's accepted tolerance at scale) |
| **Bucketed histogram for economy percentiles** (03 / Q5) | `ECONOMY_SUPPLY_DAY` seal-time percentiles over `BALANCE_SNAPSHOT` → fixed-boundary bucketed histogram (boundaries config, forward-only) | > ~1 M `BALANCE_SNAPSHOT` rows per game×currency, or the seal-time percentile scan exceeding a flush interval (~5 min) | percentiles become bucket-resolution approximations; boundary changes never retro-apply |

Reading order matters: at the §2 envelope **none** of these are flipped — exact sets, SET-marker dedup, and exact percentiles are all inside budget, which is precisely why v1 ships exact-by-default with levers *documented* rather than built.

## 7. Data erasure (GDPR/CCPA) — normative Q7 design

*This section is the **normative home** of the Q7 ruling (research §7; Foundation §9.6 points here). One idempotent erasure job, four tiers, SLA ≤ 30 days (GDPR Art. 12(3); typically ≤ 4 days).*

**Legal frame.** GDPR governs *personal data*; Recital 26 places anonymous/aggregate statistics outside it, Art. 17(3)(d) + Art. 89(1) shelter statistical processing from erasure where erasure would render it impossible, Art. 17(3)(b) preserves legal-obligation financial records, and Art. 11 says a controller need not maintain identification just to service rights requests. The results-only architecture (FR-010/SC-007) makes this cheap: **the spine family is the entire per-user data surface** (the `../metrics/README.md` ledger enumerates every draw), and it is tiny by design. The industry position is unanimous — GA4 (deletion requests with a ~72 h grace, physical erasure within a ~2-month cycle), Matomo (purge raw visitor data, keep aggregated reports), PostHog (async batched deletes), Plausible (never stores identifiers past aggregation), Snowplow (Right-to-be-Forgotten as an *offline* Spark job over stored files). We adopt the same shape.

### 7.1 Tier (a) — spine family: HARD DELETE

| Structure | Action |
|---|---|
| `USER_SPINE` (`first_seen`, `active_days_bitmap`) | delete row |
| `PAYER_SPINE_EXT` (incl. `lifetime_spend_normalized`), `PAYER_PERIOD_SPEND` | delete rows |
| `BALANCE_SNAPSHOT` (if depth mode on) | delete rows |
| `ACTIVE_USER_DAY.members`, `PAYER_DAY.payer_members` | **scrub `user_id` from the sets** for the user's activity days — a `user_id` inside a membership set is an identifier, projection or not (Foundation §9.2's caveat made binding) |
| Funnel progress rows (*conditional* — only if the 06-funnels scope is ever ratified) | join tier (a) |
| `PURCHASE_IDEMPOTENCY` | **the exception: DETACH, not delete** — tombstone/null `user_id`; keep `transaction_id`, dates, and money fields. Art. 17(3)(b) financial-records footing; keeps the **durable money dedup intact** (a deleted row would let a very-late purchase retry double-count — §F's whole reason for durability) and keeps 05's Q6 seal reconciliation (Σ cells vs idempotency day-sums) valid post-erasure. |

**Documented consequence:** stored numeric cells never change, but **cardinality-derived reads shrink** — a day's DAU/payer count read as `|members|` decreases by the erased member. Accepted: an erased person is allowed to vanish from user-counts; money day-totals are stored numerics and stand.

### 7.2 Tier (b) — aggregated day cells: LEAVE UNTOUCHED, never recompute

`SESSION_DAY_RESULT`, `EVENT_DAY_COUNT`, `ECONOMY_FLOW_RESULT` (+ segments), `COHORT`, `RETENTION_CELL`, `MONETIZATION_CELL`, `PAYER_DAY.revenue_day_total`, `EXCEPTION_TALLY`, `EVENT_CATALOG`, `ECONOMY_SUPPLY_DAY` — once the membership sets are scrubbed, none of these contains any user identifier; they are aggregate statistics under Recital 26, sheltered by Art. 17(3)(d)/89(1), and Art. 11 disclaims any duty to re-identify contributions in order to subtract them. **No recomputation, ever** — recomputing sealed cells would violate the seal invariant (Foundation §2.3) *and* is legally unnecessary. This is the unanimous GA4/Matomo/PostHog/Plausible position.

### 7.3 Tier (c) — raw S3 day files: retention-bounded expiry + ledger-refiltered rebuilds

Sealed objects are **never rewritten on the hot path** (bridge 01.5's immutability is load-bearing for SC-008). Instead:

- **Mechanism = retention expiry.** New knob **`raw_retention_days`** (default **90**; joins 07's lifecycle — S3-side expiry, distinct from `cold_storage_local_retention_days`). An operator wanting the strictest reading sets it **≤ 30**, landing physical raw erasure inside the statutory month.
- **Posture = "put beyond use"** (the ICO-accepted stance for backup media): between execution and expiry the subject's envelopes exist only inside sealed, unread, expiring objects, and the platform guarantees they can never re-enter any aggregate — because:
- **Every manual raw rebuild MUST re-apply the `ERASURE_LEDGER` as a filter step**, exactly as bridge 01.5 §5 makes it re-apply dedup: for each replayed envelope, compute the per-game keyed hash of its `user_id` and skip on match with an `executed` ledger row. Added to the 01.5 conformance checklist by reference.
- **Optional strict mode** — `strict_raw_rewrite` (default off): an operator-run **offline** tool per affected day: filter → write new object → verify → swap `object_ref` in `UPLOAD_BOOKKEEPING` → delete old object. Replace-not-append, so 01.5 immutability holds; Snowplow-R2F precedent. Never on the hot path, never default.
- **Crypto-shredding REJECTED for v1**: per-user DEKs are themselves a new durable per-user structure (violating spine minimalism) plus key-management surface; revisitable if retention windows must lengthen.

### 7.4 Tier (d) — Redis: self-erasure by TTL behind a wait-for-seal gate

**No Redis deletion code exists.** The destructive pass (§7.5) runs only **after every day the user was active in has sealed** — a wait of ≤ 72 h (open day + 48 h grace). By then: the final flush has landed the membership sets in Postgres (scrubbed there), sealed buckets are no longer swept by the flusher (no resurrection path), and every remaining Redis copy — open-bucket member entries (~72 h TTL), staging (48 h), dedup markers (24 h, keyed by `event_id`/`transaction_id`, not `user_id`) — expires within ~24 h of execution on its own clock.

### 7.5 `ERASURE_LEDGER` (new entity) and the job

```
ERASURE_LEDGER
    id    game_id        PK, FK
    id    request_id     PK
    ts    requested_at
    text  status         ∈ {pending, awaiting_seal, executed}
    ts    executed_at
    hash  subject_ref    "per-game KEYED hash of user_id — NEVER plaintext"
```

- `subject_ref` is a keyed (per-game secret) deterministic hash: recomputable at rebuild time for filtering, but the ledger itself never becomes a plaintext registry — **a spine of erased people** — which is exactly what Art. 11 says we must not be forced to keep.
- **Row expiry**: a row may be purged once `raw_retention_days` has passed every file the subject could appear in — operationally `executed_at + raw_retention_days + ~3 d` seal margin. After that no rebuildable object contains the subject, so the filter is moot.
- The ledger is **operational, request-keyed state under `GAME`** — not a §1.3 spine tier (it holds no plaintext user identifier and no behavioral data); recorded in the `../metrics/README.md` ledger as an annotation, not a per-user draw.

**Job op-order (idempotent; re-runs are no-ops on absent rows/members):**

1. **Verify** the request via the operator admin API (phase 10 surface) → ledger row `pending`.
2. **Read `active_days_bitmap` FIRST** (+ `PURCHASE_IDEMPOTENCY.purchase_day` rows) to enumerate every activity/payer day — the bitmap must be read before anything deletes it.
3. Any enumerated day **unsealed** → park **`awaiting_seal`**; re-evaluate each run (≤ 72 h in the normal case). If the id *keeps generating activity*, the request cannot converge — the admin surface flags it: account deletion in the game must precede analytics erasure; SLA holds provided the id goes quiet ≥ 72 h before day ~27.
4. **Destructive pass** (all days sealed): scrub `ACTIVE_USER_DAY.members` + `PAYER_DAY.payer_members` for the enumerated days → delete `BALANCE_SNAPSHOT`, `PAYER_PERIOD_SPEND`, `PAYER_SPINE_EXT` → delete `USER_SPINE` **last** → tombstone `PURCHASE_IDEMPOTENCY.user_id` (per `erasure_purchase_mode`).
5. Ledger row → **`executed`** + `executed_at`.

**SLA:** request → `executed` ≤ **30 days** hard (Art. 12(3)), **typically ≤ 4 days** (≤ 72 h seal wait + one job run). Raw copies persist beyond `executed` only as put-beyond-use expiring objects (§7.3).

### 7.6 Recovery-lever amendment (normative) + re-appearance

Foundation §1.3 makes projections rebuildable by spine re-scan. Post-erasure a spine re-scan reproduces counts **minus erased users**, so rebuilt projections read *below* stored sealed cells — and that is correct, not drift: **stored sealed cells are the post-erasure truth; re-scans and raw rebuilds reconcile forward only** (they must never "correct" a sealed cell downward to match a post-erasure spine). The same rule governs ledger-filtered raw rebuilds.

**Re-appearance:** the same `user_id` seen after execution is a **new data subject by construction** — fresh spine row, new `first_seen`, new cohort. There is **no denylist** and the ledger hash is never consulted at ingest: a denylist is itself a persistent record of the erased person (Art. 11 again), and no surveyed product ships one.

### 7.7 Config surface

| Knob | Default | Semantics |
|---|---|---|
| `raw_retention_days` | 90 | S3-side raw expiry (07 lifecycle); ≤ 30 = strictest reading; forward-only |
| `erasure_purchase_mode` | `detach` | `detach` (tombstone `user_id`, keep money row — default) / `delete` (operator accepts the double-count risk §F warned about) |
| `strict_raw_rewrite` | off | enables the §7.3 offline rewrite tool; operator-run, never automatic |

## 8. Relations / entities added

- **Owns:** the scale envelope + budgets (§2–§3), the backpressure posture (§4), `ingest_events_per_sec_cap` (§5, enforced by 01's door), the lever triggers (§6), and the **normative erasure design** (§7) with its job.
- **Adds:** `ERASURE_LEDGER` (operational, request-keyed, under `GAME`; §7.5 — belongs in `ER-full.md` beside `UPLOAD_BOOKKEEPING`, not in the spine tiers); config knobs `ingest_events_per_sec_cap`, `raw_retention_days`, `erasure_purchase_mode`, `strict_raw_rewrite` join `GAME.config`; proposed `EXCEPTION_TALLY` reason `rate_limited` (enum amendment, §5).
- **Writes (shared):** tier-(a) deletions touch structures owned by 02/03/04/05/06 — executed by the one erasure job under this spec's rules, the system's second cross-story write delegation (after bridge 02.5).
- **Reads:** `active_days_bitmap` + `PURCHASE_IDEMPOTENCY` (day enumeration, §7.5); Foundation §6 loss ledger (§4 cross-check).
- **Cross-links:** bridge 01.5 — rebuild tooling gains the **ledger-refilter step** (§7.3) alongside re-dedup; Foundation §9.2 — the HLL-drops-sealed-membership lever **shrinks the erasure surface** (§6 ↔ §7.1); phase 10 — hosts request verification + the `awaiting_seal` stuck-flag; SDK specs 08/09 — must honor 429/503 + Retry-After with buffered backoff (§4–§5).
- **Ordering / lifecycle:** erasure's destructive pass strictly follows the last activity day's seal (§7.4); ledger rows outlive execution by `raw_retention_days` + margin; all knobs forward-only.
