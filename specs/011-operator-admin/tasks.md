## 0. Scope & dependencies

This story builds the **operator control plane** — the single human administration surface over a self-hosted, single-tenant (multi-game-under-one-operator) platform. It delivers four things: (1) `OPERATOR_ACCOUNT` auth with TOTP MFA and brute-force lockout; (2) game registration plus the Q2 two-class credential lifecycle (`GAME_SDK_KEY` public / `GAME_SERVER_CREDENTIAL` secret) with dual-active rotation; (3) the admin surface over **every** `§6` config knob across the ops-envelope / metric stories / this story, written **forward-only** to `GAME.config` + `CONFIG_AUDIT`, honored by workers via the Redis worker-config-cache within `worker_config_cache_refresh_sec`; (4) the GDPR admin triggers — the operator-verified erasure request (drives [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §7's job) and its read-only sibling, the Art. 15/20 DSAR-access/portability export (drives [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §9's job). This story adds **no SDK contract, no envelope field, no `kind`** ([design.md](./design.md) §API surface) and **no per-user spine draw** ([design.md](./design.md) §New entities acknowledged).

**Must exist before this story starts** (per the [PLAN-INDEX](../001-analytics-platform/PLAN-INDEX.md) build order and dep table): the `GAME` registry + `GAME.config` blob owned by [002-foundation-ingest](../002-foundation-ingest/spec.md) (Foundation §5) — this story is the human write-path into it; the Foundation §4.5 ingest front-door credential-resolution contract (this story issues the credentials it resolves); the per-story `§6` knob contracts ([002-foundation-ingest](../002-foundation-ingest/spec.md) … [008-cold-storage](../008-cold-storage/spec.md), [ops-envelope.md](../001-analytics-platform/ops-envelope.md)) to validate values against; the [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §7 erasure job + `ERASURE_LEDGER` and [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §9 DSAR-access job (this story triggers, does not implement, them); the Foundation §4.7 `reporting_offset` install-time semantics.

**FR/SC this story is accountable for:** FR-001 (register multiple games, each a unique key — game_id server-derived per key class), FR-003 (authenticate every ingest request by key, reject invalid/unknown — this story issues/revokes the keys and stamps `last_used_at`), FR-020 (monetization dimensions configurable per game, forward-only — one instance of the general forward-only rule this story owns), FR-027 (**every** operational knob configurable without code changes — the full inventory admin surface), FR-029 (out-of-DB secret encryption, TLS-refusal posture surfaced, operator lockout + optional MFA), FR-030 (GDPR right-of-access Art. 15 + portability Art. 20 export).

## 2. Cross-story dependencies

- **`GAME` + `GAME.config` are owned by [002-foundation-ingest](../002-foundation-ingest/spec.md)** (Foundation §5, "written by registration/admin API", path direct). This story is the **human write-path** into a structure ingest owns — T-10.12/T-10.24/T-10.25 write it; the worker path and every story **read** it. No parallel writer: the admin API is the sole registration/config writer; ingest workers never write config, only read the cached snapshot.
- **Ingest front door (Foundation §4.5) READS the credentials this story WRITES** and stamps `last_used_at` on each use. T-10.20's `last_used_at` read and T-10.17/T-10.41's rotation-drain depend on the front door writing that telemetry; T-10.15/T-10.42's revoke effect depends on the front door failing auth on a revoked/unrecognized credential (fallback-`client` never applies to a bad credential).
- **Every worker READS the config this story WRITES, via the worker config cache** (T-10.26). The realized config-effective-time (T-10.44) is bounded by `worker_config_cache_refresh_sec`; workers own the read, this story owns the cache **contract** and the durable write. [006-monetization](../006-monetization/spec.md)/[004-economy](../004-economy/spec.md) additionally read `CONFIG_AUDIT.effective_from` (T-10.27/T-10.35) for their dimension-era / FX-era coverage caveats.
- **The [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §7 erasure job + `ERASURE_LEDGER` and the [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §9 DSAR-access job must exist before their triggers (T-10.29/T-10.30/T-10.31) can run.** This story hosts request verification + the `awaiting_seal` stuck-flag + the read-only export surface; [ops-envelope.md](../001-analytics-platform/ops-envelope.md) owns the jobs, the ledger, and the tier-(a)…(d) destructive rules. The erasure job is the system's second cross-story write delegation (after bridge [02.5-activeness-spine-contract](../001-analytics-platform/bridges/02.5-activeness-spine-contract.md)); the DSAR job is read-only.
- **The out-of-DB master key + envelope-encryption (T-10.21)** underpin [ops-envelope.md](../001-analytics-platform/ops-envelope.md) §9's lawful-pseudonymization claim for the `ERASURE_LEDGER` hash key and [008-cold-storage](../008-cold-storage/spec.md)'s `cold_storage_credentials` / [006-monetization](../006-monetization/spec.md)'s `fx_table` material; the erasure-ledger key living outside the DB ([ops-envelope.md](../001-analytics-platform/ops-envelope.md) §7.5 / §9) is a hard dependency of the erasure design's Art. 11 posture.
- **The per-knob effect-timing (T-10.23/T-10.28) reads every owning story's `§6` contract** ([002-foundation-ingest](../002-foundation-ingest/spec.md)/[003-sessions](../003-sessions/spec.md)/[004-economy](../004-economy/spec.md)/[005-retention](../005-retention/spec.md)/[006-monetization](../006-monetization/spec.md)/[007-derived-kpis](../007-derived-kpis/spec.md)/[008-cold-storage](../008-cold-storage/spec.md)/[ops-envelope.md](../001-analytics-platform/ops-envelope.md)/this story) to validate values and label behavior — read-only; this story never redefines a knob's semantics ([design.md](./design.md) §Config administration).

## 4. Open considerations / flags for /plan

- **Session store choice (below altitude).** [design.md](./design.md) §5 says "No admin-owned durable Redis state" and the worker config cache is transient. The operator **session** store (T-10.7) is unspecified — likely Redis or signed cookie; if Redis, it is a new admin-touched (though losable) Redis structure not in Foundation §2.1's owned domain tags. Flag for /plan: pick a session backend and, if Redis, register a domain tag or confirm cookie-only.
- **`worker_config_cache_refresh_sec` = config-change latency ceiling AND a hot-path read.** Default 30 s means up to a 30 s window where different workers honor different config for the same game (a rolling refresh, not atomic). [design.md](./design.md) §Config-effective-time calls this "a bounded, documented lag" — confirm no knob's correctness depends on all workers flipping simultaneously (none identified: forward-only knobs re-key by `effective_from` per cell, not by a global flip). Flag: the cache-refresh mechanism (poll vs pub/sub invalidation) is a /plan choice; poll is simplest and matches the "within one refresh interval" contract.
- **`last_used_at` write amplification.** The front door stamping `last_used_at` on **every** credential use (needed for rotation-drain, T-10.20) could be a per-event Postgres write on the hot path — contradicting the results-only / no-per-event-write posture. Flag for /plan: this likely needs throttled/last-write-wins or a periodic-flush treatment (e.g. update at most once per N seconds per credential), not a synchronous per-event write. Not resolved in the design; surfaced by building.
- **Password/credential hashing + prefix scheme (below the no-auth-library altitude).** [design.md](./design.md) explicitly excludes the auth-library choice and DDL. The password-hash algorithm, the `key_prefix`/`credential_prefix` format ([design.md](./design.md) says "prefix-typed … recognizable by secret scanners"), and the master-key envelope-encryption primitive are all /plan-level. Flag: pick argon2/bcrypt for passwords, a documented prefix convention (Stripe-style `pk_`/`sk_`-analog), and an AEAD (e.g. libsodium secretbox / AES-GCM) for the envelope.
- **Erasure/DSAR verification is a manual operator duty, not automated.** [design.md](./design.md) / [ops-envelope.md](../001-analytics-platform/ops-envelope.md) make identity verification "the studio's duty, mirroring Matomo" — the admin surface records that a verified request was made but does not itself prove identity. Flag for /plan: the verification UX (what the operator attests) and its audit trail need definition; over-trusting this surface is a data-exfil risk (a DSAR-access export is a full per-user dump).
- **`reporting_offset` set-once enforcement.** T-10.13 captures it at install and treats it as fixed, but nothing structural prevents an operator editing it later (it is a `GAME.config`/platform knob). [design.md](./design.md) / Foundation §4.7 say changing it after data exists is a forbidden forward-rebuild (out of v1). Flag for /plan: the admin surface should **hard-block or loudly gate** editing `reporting_offset` once any data exists — the config-validation layer (T-10.24) is the natural enforcement point, but the "data exists" check is an added predicate not spelled out.
- **Infra-secret rotation re-encryption is a maintenance operation touching all encrypted rows.** T-10.22's "re-encrypt under a new master key" implies a bulk re-encrypt pass over every envelope-encrypted value across games — an operational job (downtime/coordination) the design names but does not sequence. Flag for /plan: sequence the master-key rotation (dual-key read window: decrypt-old / encrypt-new) so it isn't a flag-day.
