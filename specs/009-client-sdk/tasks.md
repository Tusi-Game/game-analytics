## 0. Scope & dependencies

These two stories ship the **packaged client artifacts** — the browser/game SDK (`packages/sdk-client`, MIT, public `sdk_key`, spoofable zero-money path that owns sessions + the purchase companion) and the Node server SDK (`packages/sdk-server`, MIT, secret `server_credential`, the trusted money/economy path) — inside **one npm monorepo** they co-own (workspace layout, changesets, OIDC trusted-publish + provenance). They own **no server-side structure** (no Postgres, Redis, or `GAME.config` knob); their entire durable surface is the wire (Foundation §1.1). Per the README dependency table, **the client SDK ([009-client-sdk](../009-client-sdk/spec.md)) depends on [002-foundation-ingest](../002-foundation-ingest/spec.md), [003-sessions](../003-sessions/spec.md), [004-economy](../004-economy/spec.md), [006-monetization](../006-monetization/spec.md)** and **the server SDK ([010-server-sdk](../010-server-sdk/spec.md)) depends on [006-monetization](../006-monetization/spec.md), [004-economy](../004-economy/spec.md) + Foundation §4.5** — all of which are design-complete, so both SDKs can be built against the frozen wire contract without waiting on server-worker code (they need only a conformant mock ingest + the shared golden fixtures, which they help produce). The monorepo scaffold (§1.7) precedes both packages.

**Accountable for:** FR-005 (client buffer + batched POST + offline retry), FR-007 (server SDK, shared ingest contract), FR-008b (`client_event_time`/`client_sent_time` stamping — SDK side), FR-021 (server = trusted revenue row; client zero-money companion join), FR-008a (SDK side — per-event `event_id`, original id preserved across retry), SC-001 (live events in <15 min of integration — the US1 client half), SC-002 (fast ack, never blocks gameplay/checkout — the SDK-side non-blocking contract). Consumes locked Q2 (credential classes), Q8 (no FX on server SDK), Q9 (wire versioning), Q10 (license + npm publishing).

## 2. Cross-story dependencies

- **Wire contract (Foundation §1.1, Q9) — READ by both SDKs; OWNED by the front door ([002-foundation-ingest](../002-foundation-ingest/spec.md)).** The SDKs are *producers* against a frozen contract: `/v1/events`, `v:1`, mandatory `sdk` descriptor, additive-only fields, `game_id` server-derived. Every batch task (T-08.9/10/31/44) depends on this being final — it is (locked). The SDKs must never introduce a top-level field; that is enforced structurally at the envelope builder (T-08.14, T-08.39).
- **Provenance / credential classes (Foundation §4.5, Q2) — READ by both; the credential *registry + issuance/rotation* is OWNED by [011-operator-admin](../011-operator-admin/spec.md).** The SDKs consume only the **prefix-typing convention** to fail-fast at init (T-08.23, T-08.38); they cannot be exercised end-to-end against a live server until [011-operator-admin](../011-operator-admin/spec.md) issues a real `sdk_key` / `server_credential`, but unit/mock tests need only the prefix grammar. Rotation being dual-active (Foundation §4.5) is an [011-operator-admin](../011-operator-admin/spec.md) concern the server SDK simply tolerates (one valid credential at a time in config).
- **Shared golden fixtures + reference stream — CO-OWNED by [009-client-sdk](spec.md), [010-server-sdk](../010-server-sdk/spec.md), and [002-foundation-ingest](../002-foundation-ingest/spec.md).** One fixture set is the single source of truth: the client SDK produces most kinds, the server SDK produces the verified-purchase + server-economy rows, and **[002-foundation-ingest](../002-foundation-ingest/spec.md)'s ingest tests consume the identical files** (T-08.7, T-08.53–55). Whoever lands first writes the fixtures; the other two assert against them. This is the anti-drift seam — if the fixture directory is not shared, client/server/ingest conformance silently diverges.
- **`purchase_attempt_id` join ([009-client-sdk](spec.md) §3.2 ↔ [010-server-sdk](../010-server-sdk/spec.md) §3 ↔ [006-monetization §3](../006-monetization/spec.md)).** The client mints it (T-08.26) and stamps the companion (T-08.27); the game threads it through the store call; the **server SDK relays it onto the authoritative revenue row** (T-08.40); **[006-monetization](../006-monetization/spec.md) joins companion ↔ revenue on it**. Both SDK tasks must agree on the field name/format, and [006-monetization](../006-monetization/spec.md)'s staging/join (owned by [006-monetization](../006-monetization/spec.md)) must key on `purchase_attempt_id`, not the store `transaction_id`.
- **Session definition ([003-sessions §1](../003-sessions/spec.md)) — normative, READ by the client SDK.** The client's session tracker (T-08.16–22) *executes* [003-sessions §1](../003-sessions/spec.md); it never redefines a boundary. The terminal `session` event it emits is the sole activeness signal [003-sessions](../003-sessions/spec.md)/[005-retention](../005-retention/spec.md)/[funnels](../001-analytics-platform/funnels.md) consume. `session_inactivity_timeout_min` is mirrored from [003-sessions §6](../003-sessions/spec.md) with **no v1 sync channel** (see flag).
- **Server SDK owns no server structure.** All durable effects of the server SDK's emissions (revenue row → [006-monetization](../006-monetization/spec.md) gate 6a/6b → [05.5](../001-analytics-platform/bridges/05.5-purchase-accept-contract.md) atomic unit → [007-derived-kpis](../007-derived-kpis/spec.md)'s payer spine writes; server-economy → [004-economy](../004-economy/spec.md)'s trusted slice; catalog → [002-foundation-ingest](../002-foundation-ingest/spec.md)) are **written by those stories' workers**, not the SDK. The SDK's only obligation is a conformant wire emission.

## 4. Open considerations / flags for /plan

1. **`<org>` scope is unresolved operator input.** Both package names (`@<org>/analytics-sdk`, `@<org>/analytics-sdk-server`) and the manifests' `repository.directory`/provenance linkage carry a placeholder the design explicitly deferred to the operator ([009-client-sdk](spec.md)/[010-server-sdk](../010-server-sdk/spec.md) Design §Packaging). **The npm org must be chosen before the first `npm publish`** — trusted-publishing OIDC config and provenance attestation both bind to the concrete scope. Blocks T-08.3/T-08.6 at release time only (not development).
2. **spec.md FR-021 vs. hardened design: companion join key.** `spec.md` FR-021 (and §D) still say the companion is "**keyed by `transaction_id`**"; the 2026-07-17 hardening ([009-client-sdk](spec.md) §3.2, [010-server-sdk](../010-server-sdk/spec.md) §3, README §Adversarial hardening) supersedes this with the SDK-minted **`purchase_attempt_id`** (the store `transaction_id` join silently empties segmented dims in production). Tasks follow the hardened design (`purchase_attempt_id`). **Flag:** spec.md text is stale here — the reconciliation is documented in the story specs but the umbrella `spec.md` itself was not rewritten. /plan should confirm the platform-side join ([006-monetization](../006-monetization/spec.md)) keys on `purchase_attempt_id` to match. (READ-ONLY: not editing spec.md per brief rule 1.)
3. **Timeout-knob drift ([003-sessions](../003-sessions/spec.md) ↔ [009-client-sdk](spec.md)) — no v1 sync channel.** `session_inactivity_timeout_min` lives both in `GAME.config` ([003-sessions §6](../003-sessions/spec.md)) and as a client `init` value with **no remote-config pull in v1**; keeping them aligned is documented operator responsibility. Drift changes session *boundaries* only (the server never re-times sessions). A remote-config-at-init pull is the named future option. /plan should decide whether v1 ships any warning when the two visibly disagree, or treats it as pure documentation.
4. **`purchase_attempt_id` threading is a game-integration burden, gracefully degrading.** The join depends on the game relaying the client-minted id through `appAccountToken` (StoreKit 2) / `obfuscatedAccountId` (Play) and the server SDK reading it back. If a game cannot thread it, the companion still ships, the join simply misses, and the purchase stands with reduced dims ([009-client-sdk](spec.md) §3.2). /plan: the SDK cannot enforce this end-to-end — worth surfacing prominently in both READMEs and possibly a debug warning when `verifiedPurchase` ships without a `purchase_attempt_id`.
5. **sendBeacon 64 KB tail-flush is best-effort, not guaranteed.** The unload flush ships only the queue tail under the ~64 KB beacon cap; a hard kill mid-beacon relies on the reconcile-at-next-init backstop ([009-client-sdk](spec.md) §2.1). This is an accepted residual (terminal event near-certain, not certain). No action needed — flagged so /plan does not treat unload delivery as exactly-once.
6. **Server SDK v1 has no durable spool — process crash loses the un-acked in-memory queue.** Accepted by design ([010-server-sdk](../010-server-sdk/spec.md) §4): money recovery source is the game backend's own payment records; re-emit is safe under durable `transaction_id` dedup, and `flush_on_purchase` shrinks the window. /plan: ensure the server-SDK README's crash-recovery guidance (re-emit from payment records) is prominent, since it is the only recovery path.
7. **Storage/quota edge on the client (below task altitude).** IndexedDB availability, quota limits, and private-mode fallback-to-memory (T-08.12) vary by browser/webview; the design mandates degrade-never-throw but the concrete quota-eviction thresholds and IndexedDB schema/versioning are implementation details /plan must pin. The `crypto.randomUUID` secure-context feature-detection (T-08.11) similarly needs a tested fallback matrix (plain-HTTP origins, old webviews).
8. **Bundle-size / zero-dependency budget for the client.** "Zero runtime dependencies" is a design goal ([009-client-sdk design](design.md) §Packaging); a bundled `nanoid`/UUID fallback (T-08.11) and optional gzip (`CompressionStream`, T-08.37) must stay within that budget or be inlined. /plan should set a bundle-size budget and CI check, since bundle weight is a real adoption factor for an embeddable game SDK.
